# Complete Pipeline

## 1. Scenario Construction
Input data enters the system as a `Scenario` in `api/schemas.py`.

Scenario contents:
- tasks with durations, priorities, and deadlines
- fixed commitments such as classes and labs
- user preferences such as sleep windows, preferred study windows, and daily workload limits

Scenario sources:
- `simulation/scenario_gen.py` for synthetic benchmark weeks
- `api/main.py` for API-driven planning and replanning requests

## 2. Initial Planning Pipeline
The initial plan is generated by `scheduler/planner.py` through `solve_scenario(...)`.

Flow:
1. `scheduler/utils.py` computes blocked slots from commitments and sleep windows.
2. `scheduler/planner.py` enumerates bounded candidate layouts for each task.
3. Single-block and bounded two-chunk layouts are scored by off-window, cram, and fragmentation penalties.
4. Candidate layouts are pruned to keep the search space manageable.
5. A CP-SAT model is built with:
   - no-overlap constraints
   - daily overload limits
   - missed-task variables
   - weighted objective terms
6. The solver selects one layout per task or marks the task missed.
7. The result is returned as a `PlanResult`.

Output metrics:
- missed deadlines
- overload slots
- off-window penalty
- fragmentation penalty
- solve time

## 3. Disruption Injection Pipeline
Replanning starts from an existing `PlanResult` and a disrupted scenario.

Disruption generation lives in `simulation/disruptions.py`.

Current disruption classes:
- `urgent_commitment`
- `missed_session`
- `deadline_pull_in`
- `low_energy_day`

Each disruption changes the scenario before replanning:
- adds new commitments
- adds or modifies tasks
- reduces available capacity
- tightens deadlines or removes preferred study windows

## 4. Strategy-Aware Replanning Pipeline
Replanning is performed through `replan_scenario(...)` in `scheduler/planner.py`.

Flow:
1. The disrupted scenario is passed in together with the previous plan.
2. `scheduler/policy_profiles.py` selects a repair strategy.
3. The planner uses the strategy profile to change objective weights and replanning behavior.
4. Previous task layouts are preserved when the strategy enables stability-aware repair.
5. CP-SAT resolves the disrupted week under the new constraints.
6. `scheduler/stability.py` computes:
   - preserved blocks
   - schedule churn
   - schedule stability percentage

Fixed repair strategies:
- `stability_aware`
- `deadline_rescue`
- `load_balance`
- `focus_windows`
- `full_replan`

## 5. RL-Assisted Replanning Pipeline
RL lives in `rl/agent.py`.

The RL layer does not replace the planner. It selects which repair strategy should be used after a disruption.

Flow:
1. A base weekly plan is created with CP-SAT.
2. A disruption is applied to the scenario.
3. `encode_state(...)` converts the disrupted context into a compact state based on:
   - urgent deadline pressure
   - number of urgent tasks
   - congestion on the disrupted day
   - total demand ratio
4. The RL agent chooses a repair strategy.
5. The chosen strategy is passed into `replan_scenario(...)`.
6. The replanner generates a feasible repaired schedule.
7. `compute_reward(...)` scores the result using:
   - missed deadlines
   - overload
   - schedule churn
   - off-window drift
   - solve time
   - schedule stability

Current RL design:
- tabular policy selector
- simulation-trained
- action space equals repair strategies
- CP-SAT remains the feasibility layer

## 6. Training Pipeline
Training is handled by `train_repair_agent(...)` in `rl/agent.py`.

Per episode:
1. Generate a synthetic week.
2. Solve the initial plan.
3. Apply a disruption.
4. Enumerate repair actions by running each replanning strategy.
5. Score each repaired plan with the reward function.
6. Update the state-action table.
7. Decay exploration.

This is a one-step repair setting:
- the RL component learns which repair policy is best for the current disrupted context
- the environment reset happens every episode

## 7. Evaluation Pipeline
Evaluation is split into two benchmark paths.

### Standard planner benchmark
`benchmarks/compare.py`

Measures:
- planning quality against heuristic baselines
- replanning quality after disruptions
- breakdown by disruption type

### RL benchmark
`benchmarks/compare_rl.py`

Measures:
- learned RL policy
- fixed repair policies
- heuristic baselines
- breakdown by disruption type
- action distribution chosen by the agent

Artifacts:
- `benchmarks/latest_results.json`
- `benchmarks/latest_rl_results.json`

## 8. API Pipeline
API endpoints are defined in `api/main.py`.

Endpoints:
- `/plan`: run the initial planner
- `/replan`: run strategy-aware CP-SAT replanning
- `/train-rl`: train the RL repair selector
- `/replan-rl`: choose a repair strategy with RL and replan
- `/simulate`: run planner and replanner benchmarks
- `/simulate-rl`: run RL benchmark evaluation

## 9. Test Pipeline
Invariant tests live in `tests/test_planner_invariants.py`.

Current checks:
- planned tasks do not overlap
- plans respect commitments and sleep windows
- scheduled durations match task durations
- replans remain feasible across all disruption classes
- benchmark output includes disruption-specific breakdowns

## 10. End-to-End Summary
The complete system is:

1. Build or receive a weekly study scenario.
2. Generate an initial weekly plan with CP-SAT.
3. Apply a disruption or real-world schedule change.
4. Encode the disrupted context.
5. Let the RL agent choose a repair strategy.
6. Replan the week with CP-SAT under that strategy.
7. Score stability, deadline completion, overload, and latency.
8. Aggregate results in benchmarks and expose them through the API.

This keeps the project technically clean:
- optimization handles feasibility
- RL handles policy selection
- simulation provides repeatable training and evaluation
